# Shadowverse WB Memo: IssueからPRまで遂行する

## 目的

1つのIssueを、範囲を守った変更、検証結果、レビュー可能なプルリクエストまで一貫して
進める。PR作成は独立した作業ではなく、この遂行フローの最終工程として扱う。

## 開始時の確認

`README.md`、`AGENTS.md`、`DEVELOPMENT.md`、対象Issue、関連コード・文書、現在の
GitHub Project Statusを読む。Issueの目的、受け入れ条件、対象外、制約が不足するなら、
実装へ進まずIssueを育てる。

## 遂行

1. 作業の種類に応じて、必要な調査・設計・変更・文書化・検証を計画する。
2. 明示的な着手許可があり、Statusが適切なら `make project-status` を使って
   `In Progress`へ移す。外部変更には `CONFIRM=1` を付ける。
3. Issueの範囲を守って作業する。要件・技術方針・対象外を変える必要が出た場合は、
   根拠と影響を示して確認を得る。
4. 利用可能で関連する検査を実行する。実行できない検査は理由と影響を残す。
5. 受け入れ条件ごとに、満たした根拠または未達事項を照合する。

## レビューとPR

PR本文には変更概要、ファイル差分と変更の対応、受け入れ条件の確認、検証結果、
人間のレビュワーに特に見てほしいポイント、制約・未検証事項を含める。Issueを完了させる
PRには `Fixes #<Issue番号>` を記載する。

Codex CloudのGitHub Code Reviewが利用できない場合でも、`In Review`へ進む前にローカルの
Codex CLIで読み取り専用レビューを行う。レビュー依頼には、対象Issue番号、比較対象
ブランチ、受け入れ条件、対象外を含める。

```text
Issue #<番号>と現在ブランチのmainとの差分を確認し、受け入れ条件・対象外・回帰リスクの
観点でレビューしてください。コード、GitHub上の状態、外部サービスは変更しないでください。
```

ローカルレビューの所見と未解決事項をPR本文へ反映する。Cloudレビューは利用可能になった
場合の任意の追加レビューであり、ローカルレビューや人間の最終判断を置き換えない。

ユーザーがPR作成を明示的に許可した場合だけ、ブランチをpushして `make pr-create` でPRを
作成し、`make project-status` で対象Issueを `In Review` にする。外部変更には必ず
`CONFIRM=1` を付ける。マージ、デプロイ、IssueのCloseは、ユーザーが明示的に委任しない
限り実行しない。
